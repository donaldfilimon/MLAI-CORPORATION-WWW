# Vendored site reconciliation — design

Date: 2026-09-07
Status: approved (design), corrected 2026-09-07 20:3x after a measurement error

## Why

`vendor/` landed in `f5743ff` (PR #63) as the reconciled remains of seven
archives. It is staging, not product: nothing under it is built, linted,
tested, or deployed. This design folds the parts that carry real work into
`apps/web` and then deletes `vendor/` entirely. Git history keeps the
provenance; the manifest in `vendor/README.md` records where each payload came
from.

## Scope, and what was measured to fix it

**A correction is recorded here because the first version of this spec got it
backwards.** It compared the vendored docs corpus against
`src/data/categories/docs-nav.ts` — which holds 9 search *blurbs* totalling 594
characters — and concluded the vendored docs were ~32x richer. That is not the
comparison that matters. `apps/web` renders `/docs` from
`src/views/Docs.tsx`, and measured properly:

| corpus | prose | blocks |
|--------|-------|--------|
| `apps/web` `/docs` today | **~34,808 chars** | 180 |
| `vendor/mlai-review` docs | ~12,139 chars | 60 |

The existing page carries roughly **three times** the prose of the tree that
was going to replace it. Acting on the original spec would have deleted 34,808
characters of published documentation.

Subject overlap is small. Only `runtime` and `wdbx` appear on both sides.

- Existing only: `api`, `deployment`, `intro`, `mcp`, `personas`, `trust`,
  `wdbx-v2`
- Vendored only: `architecture`, `evidence`, `gama`, `getting-started`,
  `identity`

**So the docs work is additive, not a replacement.** Port the five
vendored-only subjects as new per-document pages. Leave `/docs` and its 34,808
characters alone, and leave the search and mobile-nav work from `0e2af60`
alone. `runtime` and `wdbx` are not ported: the existing page already covers
them, and reconciling two versions of one subject is a content judgment nobody
has asked for.

The second in-scope payload is **projects**: `vendor/mlai-review` serves
`projects` and `projects/[slug]` from `lib/content.ts`, and `apps/web` has no
`projects` route.

Two payloads are deliberately out of scope:

- **`trust`** duplicates what `apps/web` already serves across `/security`
  (a 2,173-character view), `/privacy` and `/terms`.
- **`brief`** is not a page. Its own metadata reads "Draft and export an idea
  locally. Nothing is submitted." — an interactive client-side tool with its
  own product and privacy implications. It is a feature request, and it is not
  this one.

`vendor/mlai-site` is superseded entirely: both its routes are catch-alls and
it carries nothing `vendor/mlai-review` does not, beyond an `.env.example`.

## Content model

**Port from `lib/content.ts`, not from the `.mdx` files, and add no MDX
toolchain.**

The `.mdx` files are generated artifacts — each carries the header
`{/* Generated by scripts/generate-mdx.cjs; edit lib/content.ts instead. */}`
and contains raw HTML rather than clean markdown. The source is
`vendor/mlai-review/lib/content.ts`, already typed TypeScript:

```ts
type Section = { id: string; title: string; paragraphs: string[]; code?: string; note?: string };
type Article = { slug: string; title: string; description: string; group: string; sections: Section[]; sources: string[] };
```

`apps/web` has no MDX pipeline — no `@next/mdx`, `remark`, `rehype`,
`gray-matter`, contentlayer or fumadocs — and every long-form surface here
already stores prose as zod-validated TypeScript (`blog.ts` is 46,367
characters of it). So this is a TypeScript-to-TypeScript port.

Add to `src/data/schemas.ts`, beside `BlogSchema`:

```ts
export const DocSectionSchema = BlogSectionSchema.extend({
  note: z.string().optional(),
});
export const DocsSchema = z.array(z.object({
  slug: z.string(),
  title: z.string(),
  description: z.string(),
  group: z.string(),
  body: z.array(DocSectionSchema).default([]),
  sources: z.array(z.string()).default([]),
}));
```

`BlogSectionSchema` already carries `heading`, `paragraphs`, `list`, `math` and
`code`, so the mapping is direct: `Section.title` → `heading`,
`Section.paragraphs` → `paragraphs`, `Section.code` → a single `code` entry.
`note` is the one field blog has no home for, hence the `.extend`.

The new module is `src/data/categories/docs.ts`, exporting the five ported
articles, wired into `src/data/index.ts` the way `blog` is.

**`docs-nav.ts` is NOT collapsed.** The earlier draft of this spec proposed
folding it into the new module; that only made sense while the new corpus was
believed to be replacing the page. It describes the nine sections of the
existing `/docs` page and stays exactly as it is.

## Routing

Add `app/docs/[slug]/page.tsx` and `app/docs/[slug]/client.tsx`, following
`app/blog/[slug]/` exactly rather than inventing a shape:

- `generateMetadata` delegating to a new `docMeta(slug)` in
  `src/lib/route-meta.ts`, beside the existing `blogMeta(slug): RouteMeta`,
  returning `NOT_FOUND_META` for an unknown slug as `blogMeta` does.
- `generateStaticParams` over the five slugs, so the pages prerender.

`/docs` is unchanged except that its index gains links to the five new pages.
A dynamic `[slug]` segment under `/docs` does not shadow the static `/docs`
route in the App Router, so the existing page keeps serving.

New routes register in `src/lib/route-meta.ts` and in
`scripts/generate-sitemap.ts` — `build` runs the sitemap generator before
`next build`, so an unregistered route ships without a sitemap entry and
nothing fails.

**Links use the existing `react-router-dom` shim.** That import is not a
missing dependency: `apps/web/tsconfig.json` aliases `react-router-dom` to
`src/lib/router-compat.tsx`, a deliberate compatibility layer from the
react-router → App Router migration, and ten components already import it.
New components follow the file they are modelled on. Migrating the app off the
shim is a separate job and must not be smuggled into this one.

## Search

Additive only. `src/lib/docs-index.ts` builds `SearchRecord[]` from `docNav` +
`research`; it gains a third source — the five new docs — emitting
`href: "/docs/<slug>"`. Existing `docNav` records keep their `/docs#<id>`
hrefs, and `research` is untouched.

`SearchRecord` already permits both forms; its `href` comment reads "hash for
/docs sections or a path for other surfaces". `src/lib/docs-search.ts` and
`src/components/DocsSearch.tsx` need no interface change, so the work from
`0e2af60` is extended rather than reworked.

## Projects

Port `vendor/mlai-review/lib/content.ts`'s project records into
`src/data/categories/projects.ts` under a zod `ProjectsSchema`, then add
`app/projects/page.tsx` and `app/projects/[slug]/{page,client}.tsx` on the same
pattern as docs above, registered in `route-meta.ts` and the sitemap.

`projects` is distinct from the existing `products/[slug]` and `showcase`
routes. If porting reveals that a project record duplicates a product or
showcase entry, the duplicate is dropped rather than served twice, and the
decision is recorded in the implementation ledger.

## Removal

The final task deletes `vendor/` — the whole directory, including
`vendor/README.md` and `vendor/.gitignore`. Nothing in the app may import from
`vendor/` before that point; the port copies content into `src/data`, it does
not reference the vendored trees at runtime.

## Verification

Per task, the three commands CI runs, from `apps/web`:

- `bun run lint` — `tsc --noEmit`, strict
- `bun run test` — `vitest run`
- `bun run build` — `bun scripts/generate-sitemap.ts && next build`

Acceptance for the whole change:

1. All five ported documents render at `/docs/<slug>` and prerender via
   `generateStaticParams`.
2. `/docs` still renders its existing content unchanged, and links to the five
   new pages. A test asserts the existing nav still resolves.
3. Search returns the five new records with `/docs/<slug>` hrefs while the
   existing `/docs#<id>` records still resolve.
4. `projects` and `projects/[slug]` render, and both appear in the generated
   sitemap.
5. `vendor/` does not exist.
6. `check:topology` and all three `apps/web` commands exit 0.

`scripts/crawl-links.mjs` exists and should be run once before the final
review; it catches routes that link to nothing.

## Known risk

The baseline gate has not been run in this checkout — it is a fresh clone with
no `node_modules`, so `bun install` must come first and the pre-change state
must be confirmed green before any task claims a regression. CI was green on
`f5743ff`, which is evidence for the branch point but not for this working
tree.
