# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Context
Production-grade marketing + private-console website for MLAI Corporation. **Next.js 15 (App Router) + React 19, run on Bun** — one process serves pages AND the `/api/*` route handlers (WorkOS AuthKit, protected LLM/billing APIs, inquiry storage, telemetry). The previous Vite SPA, Bun/Hono server, and Rust/Axum migration plan are abandoned. Do not extend or restore those stacks; active work belongs in the TypeScript/TSX Next.js surface.

## Essential Commands
- `bun install` — Install dependencies (Bun 1.4+; `bun.lock` text lockfile)
- `bun run dev` — Next.js dev server, port 3000 (pages + `/api/*` in one process; `./start_dev.sh` is now just this)
- `bun run build` — **Runs `bun run sitemap` first** (so detail-page URLs never drift), then `next build`.
- `bun run start` — Production server (`next start`; port 3000 by default, but it now **honors `PORT`** — the `--port 3000` flag was removed because it overrode Next's own handling, so a host that injects `PORT` bound the wrong port and never went healthy).
- `bun run lint` — Type-check (`tsc --noEmit`, TypeScript 6); the primary gate.
- `bun run test` — Vitest 4 suite in `src/__tests__/` (don't pin a file or test *count* here — it drifts every commit; a stale one was corrected on 2026-08-08). The two policy-pinning ones: [content.test.ts](src/__tests__/content.test.ts) validates content against the Zod schema (every blog/research/team slug unique + URL-safe, non-empty body); [workos-admin.test.ts](src/__tests__/workos-admin.test.ts) pins the admin-access policy (fails closed in production when `ADMIN_EMAILS` is unset, MFA gating) **and** the `getReturnTo` open-redirect guard. The rest cover pure server/lib logic — one file per module: `rate-limit` (bucket keying + window expiry; note the keying itself is `clientIpOf`, which lives in `session.ts` and is only *imported* by `rate-limit.ts`), `telemetry` (DNT/GPC opt-out gate), `route-meta` (noindex on unknown slugs + robots/canonical), `llm` (no-key safe fallback), `api` (`apiJson` error contract via mocked fetch), `wdbx-demo` (embedding/cosine/blockHash/chain), `db` (`resolveDbPath`), `session` (`clientIpOf` leftmost-XFF, `toPublicUser` token stripping, the fail-closed `SESSION_SECRET` policy, cookie flags, and seal→unseal rejection of a cookie replayed from a different IP or User-Agent), `body-limit` (the streaming byte cap, the `T | Response` contract, and the never-throw-on-abort property the csp-report route depends on), `site-accent` (the static-literal accent classes, see below), `dates`, `feed`, `structured-data`, `landing-page` (the `site/` Pages surface, see below), `design-sync` (pins `.design-sync/config.json` against the real filesystem — every non-null `componentSrcMap` entry must resolve, following one level of `export * from`, and every semantic color utility the `ds.ts` components use must have a token in `src/index.css`; catches the converter config rotting silently), `hero-signature` (source-level guards for the `BacktracePanel` hero, see the Hero visual note below), and `tag-colors`/`utils`. There are **no component/DOM tests** — the suite is deliberately Node-only, so no jsdom/RTL setup exists; adding one means adding that environment. `bun run test:watch` for the watch loop.
  - Single test: `bunx vitest run src/__tests__/content.test.ts` (one file) or `bunx vitest run -t "<name>"` (by test name). Do **not** use `bun test` — it invokes Bun's own runner, not Vitest.
- `bun run sitemap` — Regenerate `public/sitemap.xml` from the content layer ([scripts/generate-sitemap.ts](scripts/generate-sitemap.ts)).
- `bun run crawl` — Real-browser link-integrity check ([scripts/crawl-links.mjs](scripts/crawl-links.mjs), self-contained Playwright). BFS-crawls every route on :3000, click-tests each unique internal link, HEAD-checks asset links, fails on 404s/console errors; reports to stdout and exits non-zero. Needs `bun run dev` running (or `BASE_URL=` a deployed origin). **Playwright is deliberately not a root dependency** — the script resolves it from this repo *or* from the gitignored `.ds-sync/node_modules` staging dir, and prints install instructions instead of a module-not-found stack when neither has it. This is the only check that catches a dead `<Link href>` through the `react-router-dom` → `router-compat` alias under both the webpack and turbopack configs; `next build` proves pages compile, not that links resolve. (Replaced the `crawl-links.sh` + `link-crawl.py` pair on 2026-08-08 — they shelled out to a `playwright_cli.sh` wrapper under `~/.claude/skills/` that exists on no machine or CI runner, so `bun run crawl` had been failing with `FileNotFoundError`. Don't reintroduce a dependency on a wrapper outside this repo.)
- `bun run smoke` — API smoke matrix ([scripts/smoke-api.sh](scripts/smoke-api.sh)): asserts the `app/api/*` route-handler contracts (e.g. telemetry `204` accept, `DNT:1` short-circuits before the DB insert, `/api/csp-report` accepts any body shape, and oversize bodies on csp-report/telemetry/inquiries are rejected `413` unread) against a running dev server. Mirrors `src/lib/api.ts`. Two opt-in env vars keep expensive cases out of the default path: `SMOKE_WRITE=1` runs the inquiry happy-path POST (writes to `inquiries.db`), and `SMOKE_RATELIMIT=1` fires the 61-request burst that asserts the csp-report `429`.
- `bun run design-sync:css` — Compiles `src/index.css` through the repo's own `@tailwindcss/postcss` into the gitignored `.design-sync/lab-compiled.css` ([scripts/design-sync-css.mjs](scripts/design-sync-css.mjs)), the `cssEntry` that `.design-sync/config.json` hands the claude.ai/design converter. The app ships no standalone stylesheet, so without this the converter reports `[CSS_RUNTIME]` (no styles). Regenerate it every sync run; it is a build artifact, the script is the source.
- `bun run clean` — `rm -rf .next dist`.

## Architecture

### Single-process model (the key thing to understand)
Next.js serves pages and `/api/*` route handlers from one process in both dev and prod — no proxy, no port split. Route handlers live under [app/api/](app/api/) and share server logic from `src/lib/server/` (session, db, workos, rate-limit, llm).

### Frontend (`app/` + `src/`)
- **App Router**: route files live in `app/` (one `page.tsx` per route, dynamic `[slug]` dirs for blog/research/team/products). Each route's `page.tsx` is a thin server component that exports `metadata` (from [src/lib/route-meta.ts](src/lib/route-meta.ts)) and renders the real view from [src/views/](src/views/) through a **per-route `client.tsx`** (e.g. `app/links/client.tsx` is just `"use client"; export { Links } from "@/views/Links"`) — that file is the `"use client"` boundary. Follow this exact pattern when adding a route (full checklist under "Route classes" below).
- **`client.tsx` has two shapes — pick by whether the view server-renders.** Most routes use the plain re-export above. **Cinematic/browser-only surfaces** instead make `client.tsx` a `next/dynamic(() => import("@/views/X").then(m => m.X), { ssr: false, loading })` wrapper, because the view reaches for browser-only APIs that can't prerender — Canvas 2D (`src/film/neural.tsx`, the `src/design/*` boards), `window`/`matchMedia` listeners (`src/film/engine.tsx`), and `AudioContext` (`src/film/neural-voice.ts`); `TFPoseDemo` additionally loads `@tensorflow/tfjs`, which selects a WebGL backend at runtime. (Nothing in `src/` calls WebGL directly, and `regl` was removed as an unused dependency — don't reintroduce either claim.) The `app/showcase/{design,film,trailer,mega,explainer}/client.tsx` surfaces and `TFPoseDemo` use this `ssr:false` form; the standard marketing/console routes (incl. `/demo`, which renders `WdbxLiveDemo` but tolerates SSR) use the plain re-export. When adding a route, copy the variant that matches the view's browser-API needs.
- **Route classes**: static marketing/legal (`/about`, `/services`, `/docs`, `/links`, `/changelog`, `/privacy`, `/terms`, `/security`, `/benchmarks`); auth/console (`/login`, `/signup`, `/profile`, `/console`); dynamic-slug (`/blog/:slug`, `/research/:slug`, `/team/:slug`, `/products/:slug`); cinematic `ssr:false` (`/showcase` + the five sub-routes, `/tf-pose-demo`); the `/demo` interactive WDBX walkthrough; and `/financial-model` (the standalone three-statement-model tool — illustrative sample data for a fictional company, explicitly *not* MLAI's financials; keep that disclaimer in the copy).
- **`route-meta.ts` is the register; the sitemap is a filtered view of it — this is an invariant worth preserving.** *Every* route needs a `routeMetadata` entry, but a route belongs in `scripts/generate-sitemap.ts` **only if it is not `noindex`**. The six `noindex: true` entries (`/login`, `/signup`, `/console`, `/profile`, `/financial-model`, `/tf-pose-demo`) are exactly the six omitted from the sitemap — that is deliberate, not drift. So when adding a route: view in `src/views/`, `app/<route>/client.tsx` re-export, `app/<route>/page.tsx`, a `routeMetadata` entry always, and a sitemap static entry **only when the page should be indexed**.
- **`src/views/` was `src/pages/`** — renamed because Next treats `src/pages/` as the Pages Router. Don't recreate `src/pages/`.
- **Components come in two layers.** [src/components/ui/](src/components/ui/) holds the shadcn-style primitives (Button, Card, Dialog, …); [src/components/site/](src/components/site/) holds 24 **section-level blocks** built on them — `Section`/`SplitSection`, `CardPanel` (the shared bordered-shell + optional-`h3` primitive the card-shaped blocks are built on; extracted to collapse six near-identical shells), `FeatureCard`/`DeepDive`, `StatBlock`/`DataTable`/`SpecList`/`StepList`, `Callout`/`PullQuote`/`FAQList`/`Glossary`/`NextUp`/`PublicationIndex`, `ProvTag`/`ProvLegend`, `Eyebrow`/`Prose`/`AccentGlow`/`PersonaCard`/`IndexCard`/`ThroughputCard`/`HeroBench`. Build page sections from `site/` rather than re-deriving them. Three rules they enforce: they hold **no content** (everything is props — copy and figures come from `src/data/categories/*`); figures **require a provenance tag** (`StatBlock`/`ThroughputCard` take `measured | target | reported`, matching `docs/master-reference.md`); and they carry **no router dependency** (`NextUp`/`PublicationIndex` render a plain `<a>` and accept an optional `linkComponent`) — see the design-sync note below for why that last one is load-bearing.
- **`FAQ.tsx`/`Stats.tsx` deliberately do NOT use `site/FAQList`/`site/StatBlock`** — they overlap in subject, not in job, and collapsing either is a downgrade. [FAQ.tsx](src/components/FAQ.tsx) uses the animated shadcn `Accordion` in a sticky two-column layout; `FAQList` is a zero-JS `<details>` list for generic Q&A. [Stats.tsx](src/components/Stats.tsx) has a count-up animation and carries its target framing in the section chrome ("ENGINEERING TARGETS", "not guaranteed results"); `StatBlock` is static and requires a per-figure provenance tag. Both pairs coexist on purpose — don't "finish the reconciliation".
- **Never lift copy out of `src/data/categories/stats.ts` into a design-system preview or any standalone card.** Those entries (`295x`, `0.8ms`, `16.5k`) are only publishable because `Stats.tsx` wraps them in explicit target framing; lifted out of that section the framing doesn't travel and they become bare performance claims.
- **The product accent axis is not the persona color axis.** Most `site/` components take `accent?: "wdbx" | "abi" | "abbey"` → cyan / violet / emerald ([src/components/site/accent.ts](src/components/site/accent.ts)). Personas are a separate fixed mapping — Abbey emerald, Aviva violet, Abi **cyan** (`PersonaLegend.tsx`, `public/neural.js`). The *product* "abi" is violet; the *persona* "Abi" is cyan. Pick the axis that matches what you're labeling. Accent classes are static literals on purpose — `text-${accent}-300` compiles to no CSS, and [site-accent.test.ts](src/__tests__/site-accent.test.ts) pins that.
- **The cinematic + design surfaces live in their own top-level `src/` trees, not in `components/`.** The `src/views/Showcase*.tsx` files are thin: each wraps its implementation in [src/components/CinematicShell.tsx](src/components/CinematicShell.tsx) — a fixed full-screen overlay that covers the Navbar/Footer chrome and adds a back-to-`/showcase` pill. The implementations are:
  - **[src/film/](src/film/)** — the timeline animation engine and the shared scene library. `engine.tsx` (Stage/Sprite/`useTime`, a displayed `time` vs. true `clock` split so renders follow scrubber-hover but side effects don't), `easing.ts`, `primitives.tsx`/`fx.tsx`/`chrome.tsx`, `tokens.ts` (incl. the persona registry), `scenes/*`, and `narration.tsx`. The dependency order is documented at the top of `Film.tsx` — respect it; the scenes sit downstream of tokens/engine/easing.
  - **`src/trailer/`, `src/mega/`, `src/explainer/`** — the other three cinematic cuts. All four consume `src/film/`'s engine and scenes; `src/film/Film.tsx` is just the ~69s brand-film cut. Scene time slots are hardcoded `[start, end]` arrays that **must stay in sync with the narration script** in the same file.
  - **[src/film/neural-voice.ts](src/film/neural-voice.ts)** — in-browser neural TTS (Kokoro-82M via kokoro-js, ONNX Runtime Web, WebGPU→WASM). The runtime is fetched lazily from a CDN inside `NeuralVoice.load()` via dynamic import, so it never enters the server bundle or the initial marketing chunk — **keep it behind that dynamic import.** It is gesture-gated and honors `prefers-reduced-motion` (callers acting on an explicit click opt in with `force: true`); it degrades to a silent caption when unsupported. This is also what [src/components/PersonaVoices.tsx](src/components/PersonaVoices.tsx) reuses on marketing surfaces. The CDN origins it needs are the jsDelivr + Hugging Face entries already allowlisted in the CSP.
  - **[src/design/](src/design/)** — the `/showcase/design` design lab, entered through `DesignHub.tsx`, which `lazy()`-loads one board at a time (brand / system / showcase / hero / lab / marketing / console / docs) so opening the hub stays cheap. **This is real, imported source** — do not confuse it with the gitignored `ds-bundle/` described under Repository hygiene.
  - **Token scoping**: `src/design/mlai-ds-tokens.css` is imported *only* by `CinematicShell`, and applies under a `.mlai-ds` wrapper class so the ported design-system variables never leak into the site's `:root`. [src/index.css](src/index.css) remains the canonical token source for everything else — don't hoist `mlai-ds-tokens.css` to the layout or promote it to `:root`.
- **react-router compat shim**: the view components still import from `"react-router-dom"`, which is aliased (tsconfig `paths` + `next.config.ts` webpack/turbopack alias) to [src/lib/router-compat.tsx](src/lib/router-compat.tsx) — Link/NavLink/useLocation/useNavigate/useParams/useSearchParams over next/navigation. The npm `react-router-dom` package is removed; don't re-add it. The shim's `useLocation` deliberately avoids `useSearchParams()` (Suspense/prerender constraint) — pages that need live search params (Login) are wrapped in `<Suspense>` in their route file.
- Provider stack + page chrome (Navbar/Footer/skip-link/decorations) live in [app/providers.tsx](app/providers.tsx) (was main.tsx + Layout.tsx): `QueryClientProvider` → `AuthProvider` → `UIProvider`.
- Per-route SEO is data-driven from [src/lib/route-meta.ts](src/lib/route-meta.ts) (static map + blog/research/team/product slug derivers) via each route file's `metadata`/`generateMetadata`.
- API calls go through typed wrappers in [src/lib/api.ts](src/lib/api.ts), not ad-hoc `fetch` (except auth redirects).
- Path alias `@/*` → `src/*` (tsconfig paths; Next resolves it natively).

### Backend (`app/api/` + `src/lib/server/`)
- Every endpoint is a Next route handler under `app/api/.../route.ts`, sharing logic from `src/lib/server/`: `session.ts` (iron-session sealed cookie `mlai_session`, 7-day TTL, IP+UA-bound), `db.ts` (SQLite via `node:sqlite` `DatabaseSync`), `workos.ts` (AuthKit client, admin allowlist, MFA factor checks, `ADMIN_REQUIRE_MFA` fail-closed gate), `rate-limit.ts` (in-memory fixed windows), `llm.ts` (Gemini or safe scaffold), `body-limit.ts` (byte-capped body reads, below), and `authkit-entry.ts` — the shared AuthKit redirect behind **both** `/api/auth/login` and `/api/auth/signup`, which differ only in `screenHint`. Those two route files were byte-identical, so the shared rate-limit bucket, the unconfigured-WorkOS fallback, and the `getReturnTo` open-redirect guard that `workos-admin.test.ts` pins all existed twice and could drift; don't re-fork them.
- **Every POST body is byte-capped — Next 15 route handlers have NO default cap.** `bodyParser` config is Pages Router only and `bodySizeLimit` applies to Server Actions, so neither helps here; Cloud Run's HTTP/1 ceiling is 32 MB, meaning an unauthenticated POST could be made to buffer 32 MB per request. **Rate limiting caps request COUNT; this caps request SIZE — both are needed**, so don't treat one as covering the other. [src/lib/server/body-limit.ts](src/lib/server/body-limit.ts) is the single implementation: `Content-Length` is only a cheap early exit (absent on chunked requests), and the streaming byte counter is the actual guarantee. `readJsonLimited<T>(req, max)` returns `T | Response` — over the cap → 413, unparseable **or not a plain object** → 400, else the parsed value — and callers narrow with one `instanceof Response` check. **The object SHAPE is guaranteed; the FIELDS are still an assertion**, so routes validate their own fields but may assume a non-null object. That shape check is load-bearing, not tidiness: `null`, `5`, `"str"`, `true`, and `[]` are all *valid JSON*, so they used to sail past the parse and blow up on property access **outside** each route's try/catch — a body of literal `null` was a public **500** on unauthenticated `/api/inquiries` and `/api/telemetry`, breaking the latter's documented always-204 invariant. Arrays are rejected too; `/api/csp-report`, the one route with a legitimate array body, uses `readBodyLimited` instead. An aborted read collapses to `null` rather than throwing (an uncaught rejection would escape the handler as a 500), which is what preserves `/api/csp-report`'s never-5xx property; that invariant is pinned in `body-limit.test.ts`, not restated per route. Current caps: **4 KB** (`/api/telemetry`, `/api/billing/checkout`) · **16 KB** (`/api/profile`) · **32 KB** (`/api/inquiries`) · **64 KB** (`/api/csp-report`, via the raw-text `readBodyLimited` + `payloadTooLarge` pair) · **128 KB** (`/api/llm/chat`). A new POST route gets a cap sized to its real payload, not a default.
- Surface: `/api/auth/login|signup|callback|me|logout|features|verify-user|mfa-status`, `PATCH /api/profile`, `/api/llm/status|chat`, `/api/billing/plans|checkout`, `/api/inquiries` (public rate-limited POST, admin-gated GET), `/api/telemetry` (allowlisted events, DNT/Sec-GPC honored, no identifiers stored) + `/api/telemetry/summary`, `/api/csp-report` (CSP violation sink — see Security headers).
- Auth degrades gracefully when `WORKOS_API_KEY`/`WORKOS_CLIENT_ID`/`SESSION_SECRET` are unset (redirect with `?error=auth_not_configured`). Login/signup redirects are 307 under Next (were 302) — same behavior for GET redirects.
- **The OAuth `state` is a CSRF-bound envelope, not a bare return path.** It is `base64url({nonce, returnTo})`, and the nonce must match the `mlai_auth_state` cookie (HttpOnly, `SameSite=Lax`, 600s) **before the callback spends the code**. Without this the callback accepted an authorization code from any origin, so an attacker's harvested `code` minted a session for the *attacker's* WorkOS user inside the victim's browser — and the IP/UA session binding does not mitigate that, because the cookie binds to the victim's own IP and UA and validates normally. **The consequence to remember: `APP_URL` and `FRONTEND_URL` must resolve to the SAME host.** The cookie is set by whichever host served `/api/auth/login` (built from `APP_URL`) and must come back on the callback; a `www.`-vs-apex split now fails *every* login with `invalid_state` where it used to work fine. `workos.ts` warns at startup when the hosts differ — a warning rather than a throw, since a Host-rewriting proxy is legitimate. `getReturnTo` additionally rejects backslashes and C0 controls (`/\evil.com` and `/<CR>/evil.com` both resolve off-site through the WHATWG parser), and `redirectToFrontend` asserts `target.origin === base.origin` as a structural backstop so an unenumerated character still cannot escape.
- **`ADMIN_EMAILS` is filed as optional but the admin views are dark without it** — `checkAdminIdentity` fails closed in production, so `GET /api/inquiries` and `GET /api/telemetry/summary` 403 for everyone until it is set. Working as designed; listed here because it is the same "optional in the docs, required for the feature" shape that hid the `APP_URL` defect.

### Telemetry, MFA, and WDBX V2 assets
- **Telemetry (privacy-respecting):** `POST /api/telemetry` accepts allowlisted events only (`inquiry_open/submit/success/close`), honors DNT/Sec-GPC with a 204 no-store, and persists ONLY event + pathname + timestamp to the `telemetry_events` table in `inquiries.db` — no IP/UA/user id (the client IP touches only the in-memory rate limiter). Client side: `src/lib/telemetry.ts` (`track()`, sendBeacon + keepalive fallback, checks doNotTrack/globalPrivacyControl before sending); hooks live in `ui-context.tsx` (open/close) and `InquiryForm.tsx` (submit/success). `GET /api/telemetry/summary` (admin allowlist + optional MFA gate) returns per-event counts and the open→success conversion rate. Keep new events allowlisted on both sides; never add identifying fields. (CSP violation reports are **not** telemetry and must not be routed into this table — see Security headers.)
- **MFA:** policy is configured in the WorkOS Dashboard ([docs/mfa-workos-runbook.md](docs/mfa-workos-runbook.md) has the steps + lockout-safe rollout order). Code side: `GET /api/auth/mfa-status` lists enrolled factors; `ADMIN_EMAILS` allowlists admin readers; `ADMIN_REQUIRE_MFA=true` makes the admin reads (`GET /api/inquiries`, `GET /api/telemetry/summary`) fail closed (403) without an enrolled factor. The SDK's `listUserAuthFactors` exists at runtime but not in the bundled types — `src/lib/server/workos.ts` uses a narrow structural cast (`FactorListing`); don't "fix" it back to a direct call until the SDK types catch up.
- **WDBX V2 docs/PDFs:** the real Markdown documentation set from the sibling `wdbx` repo is mirrored at `public/docs/wdbx/*.md` (9 files incl. `limitations.md`) and surfaced in the Docs page `#wdbx-v2` section; research-paper PDFs (browser print-to-PDF of the live pages) live at `public/research/*.pdf`. The release note is the `wdbx-v2-release` blog entry. Re-mirror from `~/wdbx/docs/` when V2 docs change.
- **Hero visual (Lab):** the home hero's right panel is the **weighted backtrace** ([src/components/BacktracePanel.tsx](src/components/BacktracePanel.tsx)) — an answer resolved back through hash-chained evidence blocks, each with a parent hash and an authority-weight meter, accented by the persona that retrieved it. It **replaced the tri-persona particle "galaxy"** canvas: a drifting point cloud reads as generic AI and could sit on any competitor's page, whereas the backtrace is the product's own instrument (it mirrors the node-graph logo mark and the `wdbx-weighted-backtrace-memory-store` paper). Claims discipline: the trace is labelled illustrative and carries no latency/accuracy/QPS numbers. Two implementation invariants worth keeping: (1) the chain rail's `left` offset must equal the container padding plus half the node width (`px-5` + half of `w-2.5` = `1.5625rem`) or the chain visibly disconnects from its nodes; (2) the weight meter's **width** encodes the weight and motion only fills it in — animating `scaleX` on a full-width bar made every meter read `1.00` under `prefers-reduced-motion`. The faint `data-neural="net"` constellation backdrop is retained as atmosphere, so [public/neural.js](public/neural.js) is still live (it also still exposes the unused `galaxy` mode). **Unlike the galaxy (`hidden lg:block`), the panel renders on mobile too** — it is the page's most product-specific element and hiding it from phone traffic was a loss; both hero grid columns carry `min-w-0` so the panel's unshrinkable monospace hashes can't push the column past the viewport. [hero-signature.test.ts](src/__tests__/hero-signature.test.ts) pins all of this (rail offset, width-encoded meter, reduced-motion path, "illustrative" label with no ms/QPS figures, `min-w-0`, mobile mount) as source-level guards, because each one shipped once as a visual bug that no type-check or unit test catches.

### Content data layer
Site copy is a single source of truth at [src/data/index.ts](src/data/index.ts), which aggregates per-domain modules in `src/data/categories/*` (about, platform, industries, services, research, blog, team, stats, faq, products, changelog) into a `content` object, with Zod schemas in [src/data/schemas.ts](src/data/schemas.ts). **Every export the views consume must flow through `ContentSchema`** — `platform.ts` also exports `runtime` (the L1–L6 layer model + memory-model rows) and `services.ts` also exports `refusals` (the "what we say no to" callouts), both wired into `ContentSchema` as top-level keys; `about` gained `companyFacts`/`investorThesis` the same way. ### Feeds, error surfaces, and security headers
- **RSS**: `GET /feed.xml` ([app/feed.xml/route.ts](app/feed.xml/route.ts), `force-static`) is built by the pure, tested [src/lib/feed.ts](src/lib/feed.ts) from the content layer — every blog post + research publication, newest-first, XML-escaped, RFC-822 dates parsed best-effort from the human date strings (unparseable dates omit `<pubDate>`). **Advertised by `toNextMetadata()` in [route-meta.ts](src/lib/route-meta.ts), not by the layout** — and that distinction is the whole point. Next's `mergeMetadata` **replaces** `openGraph`/`twitter`/`alternates` wholesale rather than deep-merging, so for a long time every one of the 30 routes silently discarded the layout's feed link, `og:image`, `og:site_name`, and `twitter.images`: `curl / | grep og:image` returned **zero**, and `app/not-found.tsx` was the only page still carrying them, purely because it is the only page that sets no `openGraph`. The layout's copies are still live for exactly that page, so don't delete them as redundant. [feed.test.ts](src/__tests__/feed.test.ts) pins completeness/ordering/escaping — new content flows in automatically; keep slugs/dates valid and the test stays green. Date parsing itself lives in [src/lib/dates.ts](src/lib/dates.ts) (`parseContentDate`/`toIsoDate`/`toSitemapDate`), hoisted out of `feed.ts` so `route-meta.ts` can reuse it too without a `route-meta.ts` ⇄ `feed.ts` import cycle. **[src/lib/byline.ts](src/lib/byline.ts) exists for the same reason** — the content layer joins multi-team bylines with a **middle dot** (`"MLAI Research · WDBX Core"`), and both `route-meta.ts` (`article:author`) and `structured-data.ts` (`schema.org` authors) must split on it. They each had their own copy, each split on `","` only, and so each emitted the whole string as one nonexistent author. `structured-data.ts` already imports `SITE_URL` from `route-meta.ts`, so the shared helper could not live in either file without a cycle. Two copies is how they drifted; use `bylineNames` rather than adding a third.
- **`llms.txt`**: `public/llms.txt` (llmstxt.org convention) is regenerated by `scripts/generate-sitemap.ts` in the same pass as `sitemap.xml` — same content source, same `bun run sitemap`/`build` trigger, so it cannot drift the way a hand-written file would. Links a curated set of static marketing pages plus every product/research/blog/team-profile entry with real titles/descriptions pulled from `route-meta.ts`/`content`.
- **Per-route Open Graph**: [src/lib/route-meta.ts](src/lib/route-meta.ts)'s `RouteMeta` carries an optional `ogType` (`"article"` for blog/research, `"profile"` for team, default `"website"`) plus `publishedTime`/`authorName`, consumed by `toNextMetadata()` to emit correct `og:type`/`article:published_time`/`article:author`/`profile:first_name` tags — previously every route (including individual posts) declared `og:type=website`.

Previously every route — including individual blog posts and research papers — shared the one site-wide `public/og-image.png`, so link previews didn't reflect the actual title. Fonts: Spectral Bold is fetched once (module-memoized) from the same OFL source `scripts/generate-og.py` uses; a failed fetch (offline build) falls back to Satori's built-in sans rather than failing the build.
- **JSON-LD per detail page**: [src/lib/structured-data.ts](src/lib/structured-data.ts) builds `BlogPosting`/`ScholarlyArticle`/`Person`/`SoftwareApplication` objects from the matching content entry; each of the four dynamic `page.tsx` files (server components) renders one inline `<script type="application/ld+json">` alongside the view when the slug resolves, and renders nothing extra when it doesn't (no schema for the 404 case). Kept deliberately unenriched — no invented pricing/availability claims (matches the external-claims-audit discipline below).
- **Error/loading boundaries**: [app/error.tsx](app/error.tsx) (route-segment, renders inside the layout, brand-styled, offers reset), [app/global-error.tsx](app/global-error.tsx) (root-layout failure; self-contained `<html>` with inline brand tokens — global CSS may not have loaded), [app/loading.tsx](app/loading.tsx) (quiet cyan pulse on the ink canvas), and the 404 trio [app/not-found.tsx](app/not-found.tsx) → `app/not-found-client.tsx` → [src/views/NotFound.tsx](src/views/NotFound.tsx) (the same server-page → `client.tsx` → view split the normal routes use). Error boundaries deliberately do NOT ship error payloads to telemetry (event-allowlist policy).
- **Security headers** live in [next.config.ts](next.config.ts) `headers()`: CSP (allowlists jsDelivr + Hugging Face for the Kokoro voice runtime, storage.googleapis.com for PoseNet checkpoints, GitHub avatars, Google Fonts; `'unsafe-inline'` script/style is required by Next hydration + JSON-LD + Framer/KaTeX inline styles), HSTS (2y, preload-ready), nosniff, `X-Frame-Options: DENY` + `frame-ancestors 'none'`, Referrer-Policy, Permissions-Policy (`camera=(self)` kept for /tf-pose-demo). When a surface gains a new external origin, extend the specific directive — never widen to a bare `https:` wildcard.
- **CSP violation reporting**: because that allowlist is hand-curated over a moving surface (a jsDelivr version bump, a new Hugging Face host, a new avatar origin), the policy carries **both** `report-to csp-endpoint` and `report-uri /api/csp-report` — keep both; `report-to` is current but Safari and older Firefox still only implement `report-uri`. The `Reporting-Endpoints: csp-endpoint="/api/csp-report"` header names the group, same-origin so reports land in the app's own logs. [app/api/csp-report/route.ts](app/api/csp-report/route.ts) `console.warn`s the raw body (truncated) and returns 204. **It deliberately does NOT write to `telemetry_events`** — reports carry full URLs and User-Agent context, which would break that table's "allowlisted event + pathname + timestamp, no identifiers" contract; they go to stdout only, under the platform's own retention. It is intentionally unauthenticated (an anonymous visitor hitting a broken policy is exactly the case worth hearing about) — which is safe only because it is **rate-limited at 60s/60 per client IP** via `rateLimit("csp-report", …)`, the same window as `/api/telemetry` and for the same reason: unauthenticated, machine-emitted, near-duplicate traffic. Don't retune it to an `inquiries`-shaped 5/5min — one broken directive legitimately emits tens of un-batched reports on a single page load. The guard must stay the **first** statement in the handler, before the `readBodyLimited(req, 64 * 1024)` call buffers up to the cap — a limiter placed after it has already paid the per-request cost it exists to avoid.
- **Raster brand assets**: social crawlers ignore SVG `og:image` and PWA installs want raster icons, so `public/og-image.png` (1200×630) + `apple-touch-icon.png`/`icon-192.png`/`icon-512.png`/`icon-maskable-512.png` are generated by `bun run og` from the same geometry/tokens as the SVG originals (which remain canonical for in-app use). `manifest.webmanifest` and `app/layout.tsx` reference the PNGs. Re-run `bun run og` after any brand re-skin.
- **The `site/` GitHub Pages landing page is a second, standalone web surface** — [.github/workflows/pages.yml](.github/workflows/pages.yml) uploads ONLY `site/` as the web root, so it can't reference `public/` or `/_next/`; brand assets are physically duplicated into `site/` (`favicon.svg`, `og-image.png`, `apple-touch-icon.png` — refresh them alongside `bun run og` after a re-skin). It sets `rel=canonical` to `https://mlai-corp.com/` so it never competes with the real site for ranking, carries a full OG/Twitter card with absolute canonical-host image URLs, and matches the brand fonts (Spectral display + Geist body). [landing-page.test.ts](src/__tests__/landing-page.test.ts) pins all of that against drift, and the Pages workflow runs that single test before publishing — so a broken or drifted landing page can't ship.
- **`robots.txt` must not `Disallow` the noindex routes** — and this is a trap worth not re-falling into. `/console`, `/login`, `/signup`, `/profile` were both `Disallow`ed *and* `noindex`ed, which is self-defeating: a disallowed URL is never fetched, so a crawler can never see the `noindex`, and a robots-blocked URL can still be indexed as a bare URL entry when something links to it — and the Navbar links to `/login`. The `Disallow` lines were removed 2026-08-09; `noindex` (emitted by `toNextMetadata` for all six routes) is the mechanism that actually works. Don't "tighten" this by adding them back.
- **Disclosure**: [public/.well-known/security.txt](public/.well-known/security.txt) (RFC 9116) points at `security@mlai-corp.com` + `/security`; bump `Expires` annually.

## Deployment
Multi-stage [Dockerfile](Dockerfile) (`oven/bun` base) targeting Google Cloud Run; the runner executes `next start` on the injected `PORT` as a dedicated non-root user, with a `HEALTHCHECK` (Bun's built-in `fetch`, no extra binary needed in the `-slim` image) and a chowned `/app/data` mount point for SQLite (see `DATABASE_URL` below). **The Dockerfile prepares that mount point but the deploy never attaches a volume, so on Cloud Run `/app/data` is the container's own in-memory layer** — inquiries and telemetry die on every recycle and every redeploy. `--max-instances=1` is set as an explicit **stopgap**: it fixes the sharding half (instance #2 reading an empty DB while #1 held the rows) and costs availability, since one instance is then the whole capacity ceiling. GCS FUSE is documented in [docs/deploy-cloud-run.md](docs/deploy-cloud-run.md) but deliberately **not adopted** — it provides no file locking ("last write wins"), so SQLite on it can corrupt; a real fix is Cloud SQL, which is a `db.ts` change. Required secrets: `WORKOS_API_KEY`, `WORKOS_CLIENT_ID`, `SESSION_SECRET` (generate with `openssl rand -base64 32`). **`APP_URL` is REQUIRED in every deployed environment — it is not optional, and calling it optional is what hid the defect.** `REDIRECT_URI` is built from it, so an unset `APP_URL` ships `http://localhost:3000/api/auth/callback` to WorkOS and **login fails for every visitor**; because `--set-env-vars` *replaces* the whole env set, a value set by hand in the Cloud Run console is wiped by the next deploy. It is now a repo variable and the deploy **fails fast** if unset. `FRONTEND_URL` is genuinely optional and must be omitted rather than set empty (`?? APP_URL` does not catch `""`), and when set it must share `APP_URL`'s host — see the auth-state note above. Also optional: `GEMINI_API_KEY`, `STRIPE_PAYMENT_LINK`, `ADMIN_REQUIRE_MFA`, `DATABASE_URL` (defaults to `inquiries.db` relative to CWD; accepts a bare path or a `sqlite://`-prefixed one — resolved by the pure, tested `resolveDbPath()` in [src/lib/server/db.ts](src/lib/server/db.ts)). Copy `.env.example` → `.env` for local setup. Keep production LLM keys server-side only.
- **CI**: [.github/workflows/ci.yml](.github/workflows/ci.yml) runs `bun run lint` → `bun run test` → `bun run build` on every push/PR to `main` (the build step also regenerates `sitemap.xml`/`llms.txt`, so content/slug drift fails CI too). Separate from the two deploy workflows (`deploy-cloudrun.yml`, `pages.yml`), which are unconditional pushes to `main` — CI is the actual merge gate.
